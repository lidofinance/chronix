# Plan: standalone Chronix client

Working plan for extracting the Chronix HTTP client into a reusable package. Updated after every
step.

## Goal

A client for Chronix's control API that works in Deno and Node, is installed straight from GitHub
(`npm i github:lidofinance/chronix#<tag>`) or as a git submodule, is covered by its own tests, and
publishes an OpenAPI description generated from the same types.

## Design

- `client/types.d.ts` is the only place with types: the `Commands` table (method → params tuple and
  result), every public type and the `ChronixClient` class declaration.
- `client/mod.js` is plain JavaScript checked against `types.d.ts` (`// @ts-check`, `@implements`,
  `@type` on each method). It has no runtime dependencies and no build step; `exportSnapshot` loads
  `node:fs` lazily.
- `package.json` at the repository root describes only the client: `exports` → `types.d.ts` and
  `mod.js`, `files` → the `client/` files. No dependencies, no `prepare`.
- `src/api.ts`: `Devnet extends ChronixClient` and adds `start`, `fromSnapshot`, `close` and
  `waitForService`. `new Devnet(url)` keeps working.
- Controller: `POST /control/{method}` with the params array as the body, next to the existing
  `POST /control`. Command dispatch is checked exhaustively against `Commands` at compile time.
- `client/openapi.json` and `docs/control-api.md` are generated from `types.d.ts` by
  `deno task docs:api`: the existing zero-dependency generator (`deno doc --json` → OpenAPI 3.1,
  formerly snapshots only) now covers every command, so no generator dependency is added.
  `deno task check` verifies freshness. `deno doc` drops `?` on tuple elements, so optional
  parameters are spelled as alternative tuples (`[id] | [id, operationId]`).
- Server types (`Genesis`, snapshot records, `ManagedValidator`, `ClientRole`, `WarpOptions`,
  `ControlError`) are re-exported from `client/types.d.ts`; compile-time checks keep the runtime
  lists (`specOverrides`, `clientRoles`, profiles, the controller's command table) equal to them.
- The experiment that chose JS with checked `.d.ts`: sync errors (wrong type, missing method, wrong
  arity, wrong command) fail `deno check` and `tsc --checkJs`; `// @ts-self-types` must not be used
  in `mod.js` because it disables checking of the implementation.
